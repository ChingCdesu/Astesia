# Release memory measurements — 2026-09-05

All seven optimization findings were implemented. The largest measured reductions are in streaming
export and restore. These measurements describe the exact workloads below; they are not an estimate
of every engine or a promise about arbitrary database sizes.

## Measured workload results

Numbers are **median lifetime peak physical footprint in MiB**, from three fresh release-test
processes per workload. Each process includes its own runtime overhead. RSS was recorded as context
and is not used for the comparisons.

| --- | ---: | ---: | ---: |
| SQLite query fetch | 297.39 | 132.44 | 55.5% |
| CSV SQL export | 381.42 | 9.06 | 97.6% |
| JSON SQL export | 297.42 | 9.09 | 96.9% |
| XLSX SQL export | 410.24 | 9.55 | 97.7% |
| SQLite backup | 128.14 | 19.33 | 84.9% |
| SQLite restore | 249.20 | 10.69 | 95.7% |
| Table chart load | 266.45 | 143.08 | 46.3% |
| Query / chart workflow | 390.91 | 152.22 | 61.1% |

The query/chart fixture's **retained** physical footprint while Chart was hidden fell from
**269.06 MiB to 152.17 MiB**. Opening Chart no longer creates a duplicate row
dataset. The query/chart process uses GPUI's TestAppContext; these figures include the production
state/model/view logic but do not represent a real window's GPU allocation.

## Native application measurement

The ordinary release executable was also launched and sampled with macOS `footprint`.
The initial 67.8 MiB reading was later found to be the startup/loading screen waiting for macOS
Keychain access, so it is **excluded from workspace-idle comparisons**. A subsequent post-change

## Changes and boundaries

1. Query results are shared immutably with charts. Hidden charts do not retain result data, and
   mapping choices survive refreshes and view changes.
2. PostgreSQL, MySQL, SQLite, and SQL Server decode rows incrementally. MCP retains its requested
   limit plus one truncation sentinel and drains the rest without decoding. Limits do not rewrite
   SQL, suppress late execution errors, or interrupt mutation execution.
3. CSV/JSON SQL exports use a bounded row channel and buffered file output. XLSX uses constant-memory
   worksheets. Backup drains each page through the same atomic output boundary. Cancellation and
   fatal failure leave the previous destination intact; Partial remains explicitly Partial.
4. Table charts take ownership of fetched rows. Obsolete loads cancel between fully drained pages,
   preserving driver protocol state, all-row behavior, mappings, and the last usable chart on error.
5. Redis collection inspection uses 256-entry list/sorted-set ranges and hash/set scan cursors.
   Rows are virtualized; bounded previews retain full copy and mutation identities. Redis COUNT is
   a hint, so compact scan encodings can still return more than 256 entries. Generic full-value
   export and explicitly entered raw commands keep their existing full-result semantics.
6. Restore validates the full script into a private temporary spool before applying statements,
   then retains one statement at a time. The common tokenizer handles chunk boundaries, UTF-8,
   engine quoting, comments, and PostgreSQL dollar blocks. Changing the source file after validation
   cannot change the executed input.
7. Completion caches retain at most 16 targets and 64 column-table entries per target, with session
   lifecycle eviction. Task history retains all active tasks and the latest 256 terminal tasks;
   the Task Center states this scope. Refresh events are coalesced. Completion notifications carry
   immutable summaries, so eviction cannot erase a pending terminal notification.

Full query results and all-row charts still require memory proportional to the retained data.
A single very large cell or SQL statement can still dominate a buffer. The generic ClickHouse,
MongoDB and raw Redis query-stream fallback still materializes results; the four native SQL
adapters above are the incrementally decoded paths measured/changed here.

## Validation and tradeoffs

- Release build and release Clippy across all targets passed. Existing unused-code and pre-existing
  lint warnings remain; the new cache type-complexity warnings were removed.
- 387 regular Rust/GPUI tests passed; 9 environment/measurement tests remain ignored by default.
  The MCP binary's test also passed.
- Disposable local seven-engine connection/browse, transfer/export, and chart/diagnostic workflows
  passed. The separate live Redis test traversed 700-entry collections and checked order,
  missing/type-changed keys, shrinking pages, TTL, and full Unicode mutation identities.
- All original tokenizer tests plus chunk-boundary and malformed-input tests passed. A separate
  differential harness matched the original tokenizer on 50,000 generated fragments across five
  SQL engines, including statement-at-cursor behavior.
- CSV and JSON outputs match byte-for-byte. Backup matches after excluding its timestamp comment.
  XLSX validation checked all 300,003 cells, types, row counts, headers, widths, freeze panes, and
  autofilter; content and presentation are equivalent.
- The repeated-text XLSX fixture grows from 1,320,704 to 1,853,708 bytes (40.4%) because
  constant-memory worksheets use inline strings. Export/restore also trade memory for temporary
  file I/O. Timings are logged but were not treated as a controlled speed benchmark.
- Native startup/interaction verification must be distinguished from the GPUI TestAppContext and
  engine checks; see the native measurement status above.

## Repeating the workloads

Create a fresh disposable fixture directory with `python3 scripts/create-memory-fixture.py <dir>`.
Build the tests with `rustup run 1.97.1 cargo test --release --locked --lib --no-run`, then use the
reported `app_lib-*` executable:

```sh
python3 scripts/measure-release-memory.py \
  --test-binary <release-test-executable> \
  --fixture <dir>/fixture.sqlite3 \
  --output-dir <dir>/measurements \
  --label after
```

Use the same immutable fixture for both binaries. The ignored workloads are
`application::memory_workloads::release_memory_workload` and
`ui::query_item::tests::release_memory_query_chart_workload`. Release memory tests are opt-in and
must not be mixed into ordinary parallel test-suite runs.
